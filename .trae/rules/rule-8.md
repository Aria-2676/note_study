规范 8：插件边界

适用：写 `core/extension/`、定义插槽与钩子、判断某能力该进主包还是做插件、给插件开数据接口。
**这张卡从 v6 骨架开始就生效**，其余规则卡仍只描述 v5 存量代码。

依赖方向（铁律）
- 主包**不得 import 任何插件实现**。插件是运行时产物，编译期不存在。
- 插件**不得 import 主包源码**，只能经 bridge 调白名单 API。
- `core/extension/` 只依赖 `core/` 内部，不得依赖 `modules/`。

准入判断（能力放哪）
按顺序问，命中即止：
1. 被两个以上插件依赖 → 主包提供**框架**（不含具体实现）
2. 需要系统能力（通知/后台/小组件） → 主包提供**能力**
3. 其余 → **插件**

货币就是例子：框架（注册表 + 统一接口）在主包，能量/积分的**实现**全在插件。

三种扩展位，限制各不同
| 类型 | 允许 | 禁止 |
|---|---|---|
| 页面级 | 插件自带 HTML/CSS/JS，WebView 承载 | 访问原生能力（须经 bridge） |
| 区域级（插槽） | 只返回文本/数字/枚举 | 返回 HTML、颜色、字号、CSS；改布局 |
| 服务级 | 换算法实现 | 改表结构；同时存在多个实现 |

钩子
- 是**通知**，不是拦截——插件拿不到"取消这次操作"的权力
- 超时（>500ms）或报错 → 记日志，继续主流程，**绝不让插件阻塞主流程**
- **无人订阅时，主流程必须完整可用**（这是插件的存在前提）

数据
- 插件表统一 `plg_<插件id>_` 前缀，各自在 `plg_migrations` 记版本
- 主包迁移流程**不得感知**插件表
- 插件设置键用 `plg.<id>.*`，不得占用主包 key
- 插件**不得直接读写主包表**，只能走 bridge API

失败隔离
- 插件崩溃不得影响主包存活
- 安装/更新失败 → 回滚到上一可用版本，不留半旧半新

测试
- 每个插槽的数据契约要有测试（返回形状不对时主包如何降级）
- 钩子必须有两条测试：**无人订阅**、**订阅者超时**
