# 编辑 / 添加面板的插件化（规划，未实现）

> 2026-10-26 ｜ 状态：**只记录设计，没有代码**
> 目的：V5 靠一堆开关实现了"部分自定义"，V6 想把自由度再往前推一步，
> 同时**不让未来的插件能力逼着现在的主包返工**。

## 1. 硬约束（决定了能做到什么）

插件**不能提供 Dart UI 组件**（release 里 AOT 成机器码，没有运行时加载）。
所以"插件给我一套更漂亮/更自由的面板"只有三种落法：

| 路径 | 谁能决定 | 观感 | 代价 |
|---|---|---|---|
| A 设置项 | 主包内置几种，用户选 | 原生 | 便宜，但**不是插件** |
| B 字段清单（DSL） | 插件声明字段/顺序/显隐，主包渲染 | 原生 | 中等；DSL 会持续长大 |
| C 整页接管 | 整个添加/编辑页是 WebView | 割裂 | 大；要"宿主等插件返回"的新协议 |

**推荐 B。** A 用在"只有外观差异"的地方（日期选择器皮肤、主题）；
C 只在将来真要"完全不一样的编辑器"时才考虑，它跟主包字段是两套东西，混不起来。

## 2. B 方案的具体形状

插件在 `plugin.json` 里多一段：

```json
{
  "panels": {
    "taskEditor": {
      "fields": ["title", "tags", "estimatedMinutes"],
      "extra": [
        { "id": "energy", "type": "choice", "label": "精力消耗",
          "options": ["低", "中", "高"], "default": "中" }
      ]
    }
  }
}
```

主包按这份清单渲染成**一列原生控件**，顺序与显隐由清单决定。

### 字段分三层（2026-10-26 修订：核心字段不止三个）

用户提出"核心字段还要加"。同意，但**必须分层**——否则每加一个字段，
就要在 DSL 里多一条"能不能隐藏/能不能排序/能不能和插件字段联动"的判断，
规则会越滚越复杂。

| 层 | 字段 | 插件能不能动 |
|---|---|---|
| **L0 本体** | 标题、日期、保存/返回 | **完全不能**。没有标题任务无法显示，没有日期任务归不到某一天 |
| **L1 常用** | 描述、优先级、预计时长、标签 | 能隐藏、能改顺序，**不能改成别的语义** |
| **L2 扩展** | 插件自定义字段（KV 存） | 插件自己增删，主包只管渲染 |

**V5 里那"一堆开关"，其实就是 L1 的显隐开关。** V6 的变化不是"多几层自由"，
而是把这份开关表交给插件声明 —— 能力是同一档，维护成本却从"主包写死"变成"数据驱动"。

字段总量建议控制在 L0+L1 = 6 个以内。再加字段（循环、提醒）时**必须走同一套三层规则**，
不许开特例 —— 特例是 DSL 腐化的开始。

### 值存哪

- **核心字段**：仍然写 `tasks` 表（标题、日期、优先级、时长、描述）
- **插件自己加的字段**：**绝不进 `tasks` 表**。走 `settings` 表的
  `plg.<pluginId>.task.<taskId>.<fieldId>`，或者插件自己的 `plg_<id>_*` 表。

这条现在就要定，因为它决定"卸载插件后任务上会不会留一堆孤儿列"。
定成 KV 之后，卸载插件连带删 `plg.<id>.` 前缀即可。

### v1 明确不做

- **条件联动**（"选了 A 才显示 B"）：会立刻催生表达式引擎，是无底洞
- **嵌套布局 / 分栏 / 折叠区**：只做一列，顺序即布局
- **插件自定义控件类型**：只允许 `text` / `choice` / `toggle` / `number` 四种
- **编辑页整体布局替换**：那是 C，不是 B

## 3. 现在为了不返工，值得先做的两件事

1. **把编辑页字段抽成一份"字段清单"**（主包内部结构，不接 JSON）：
   页面按 spec 列表渲染，而不是手写六个 Widget。这样将来解析插件 JSON
   只是"换一个数据源"，不用重写页面。
   **不做也可以，但越晚做越贵**——字段还会继续加（循环、提醒）。
2. **插件字段值走 KV 的约定先写进 `plugin-contract.md`**，
   避免将来有人图省事往 `tasks` 表加列。

## 4. 编辑器的呈现形态（全屏页 / 底部弹层）

用户更喜欢 V5 的**底部弹层**，V6 现在做的是全屏页。这里同样要先说清：

**形态也属于"渲染"，插件做不了。** 能做到的是主包把两种形态都实现，然后：

| 方案 | 说明 | 评价 |
|---|---|---|
| **A 设置项**（推荐） | 默认底部弹层（可上拖到全屏），设置里可切"总是全屏" | 可预期，用户一次选完就不变 |
| B 自适应 | 按字段数/内容高度自动选 | 不建议：形态随插件字段变化而变，肌肉记忆被打断，用户无法预期 |
| C 插件决定 | — | 做不到（插件不能提供 UI） |

实现上把编辑页拆成 **「编辑器主体」+「容器」**：主体是一列字段 + 保存/删除，
容器是 `Scaffold`（全屏）或 `DraggableScrollableSheet`（弹层，上拖即全屏）。
两种形态共用同一份主体，不会分叉。

**默认取弹层**的理由：编辑任务通常是"改一两个字段"，弹层保留了列表上下文；
真正长表单（插件加了很多字段）上拖一下就是全屏，不需要两个入口。

## 5. 日期选择器

- 中文问题已解决（`localizationsDelegates`，不需要插件）
- **换皮肤**是 A 路径（主包内置多套 + 设置项），不是插件
- 真要"插件提供选择器"，只能走 C：编辑页里点日期 → 打开声明 `picker:date` 的插件页 →
  通过 bridge 回传结果。这需要新增"宿主等待插件返回"的协议，属于新机制，暂不做
