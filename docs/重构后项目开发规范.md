## 二、核心架构规范

### 2.1 整体架构原则

1. 项目基于 **Flutter + Provider**。核心业务状态由独立 Provider 封装，**禁止跨 Provider 直接耦合**；
   需要依赖时通过构造函数注入或 `ChangeNotifierProxyProvider`，不得让 Provider A 直接 `new` Provider B。
2. 基础服务（`WidgetService`、`StatisticService`）在 `main.dart` 中初始化，遵循
   **「基础服务优先、业务 Provider 后置」**：`WidgetsFlutterBinding → WidgetService →
   StatisticService → PomodoroServices → SettingsProvider → runApp`。
3. UI 层只通过 `Provider.of` / `Consumer` 读取业务数据；**禁止在页面内实例化 Provider**，
   也禁止在页面内直接改 Provider 的内部字段。

### 2.2 Provider 状态管理规范（强制）

#### 2.2.1 注册规则

1. 全部 Provider 在 `main.dart` 的 `MultiProvider` 中**集中注册**，禁止页面内零散注册。
2. 无依赖者用 `ChangeNotifierProvider`；依赖型用 `ChangeNotifierProxyProvider`：
   - `create` 中经 `context.read<依赖>()` 注入；
   - `update` 中刷新依赖引用，并**必须判空**（`shopProvider!..updatePointsProvider(...)`）；
   - `update` 里**只更新引用，不写业务逻辑**。
3. 注册顺序：无依赖在前，依赖型在后（依赖者不能早于被依赖者创建）。

#### 2.2.2 使用规则

1. 取用方式：
   - 只读不监听 → `Provider.of<T>(context, listen: false)`；
   - 需要刷新 → `Provider.of<T>(context)` 或 `Consumer<T>`；
   - **非 Widget 层**（Adapter / Service / Repository）**禁止** `listen: true`。
2. `notifyListeners()` 只在**业务状态真发生变化**时调用；禁止在统计、日志等旁路逻辑里触发。
3. 职责边界（v2.0 按现状补全，共 11 个）：

   | Provider | 核心职责 | 不应处理 |
   |---|---|---|
   | `AppStateProvider` | 全局应用状态 | 业务数据增删改 |
   | `SettingsProvider` | 设置（主题/语言/开关） | 统计上报、业务计算 |
   | `PointsProvider` | 积分增减与查询 | 商城兑换、任务完成 |
   | `ShopProvider` | 商品与兑换 | 积分计算、任务状态 |
   | `TaskProvider` | 任务增删改查与完成 | 积分发放、商品管理 |
   | `TagProvider` | 标签管理 | 任务逻辑、积分 |
   | `PomodoroProvider` | 番茄钟计时与记录 | 任务、积分 |
   | `ScratchProvider` | 刮刮乐玩法状态 | 通用积分规则 |
   | `StatisticsProvider` | 统计查询视图 | 埋点写入（走 `StatisticService`） |
   | `GameProvider` | 小游戏目录/安装/计分 | 积分规则实现 |
   | `AppUpdateProvider` | 更新检查与决策状态 | 下载安装的实现细节（委托 launcher） |

4. **新增 Provider 前先问**：能否并入既有 Provider？只有职责确实独立才新建，并在上表登记。

## 三、统计系统开发规范（核心）

### 3.1 架构原则（强制）

1. 统计采用**「统一 Service + 业务适配器」**模式，核心类 `StatisticService`。
2. 所有埋点**必须**经 `StatisticService.report()`（或 `reportBatch()`）写入；禁止：
   - 为单个模块另写一套统计接口；
   - 直接读写 `SharedPreferences` 里的统计缓存。
3. `StatisticService.init()` 在 `main.dart` 中 `WidgetService.init()` 之后执行。

> **v2.0 更正**：v1.1 §3.4.2 称统计数据会「服务端上报」、接口地址配在 `config/env.dart`。
> 这与现实不符 —— 本项目**没有 `env.dart`，也没有任何统计上传通道**，
> 统计当前**纯本地**（SharedPreferences 缓存 + 上限 2000 条 + 超限丢弃最早）。
> 相关条款已按下文重写。引入上传能力时必须先修订本节。

### 3.2 适配器规范

1. 命名：`[模块]StatisticAdapter`，与对应业务模块一一对应。
   现有适配器：tasks / shop / points / tag / pomodoro / scratch / profile / games
   （另有基类 `core/services/base_statistic_adapter.dart`）。
2. 职责：只做「取 Provider 数据 → 组装 `StatisticData` → 调 `report`」，
   **禁止在适配器里写业务逻辑**，也禁止调用 Provider 的 `notifyListeners()`。
3. 新增模块接入流程：

   ```
   Step1: 定义 XXXStatisticAdapter，经 Provider.of<T>(context, listen: false) 取数；
   Step2: 在适配器中封装该方法（如 reportPageView / reportClick / reportCount）；
   Step3: UI 层调用适配器方法，禁止直接调用 StatisticService；
   Step4: 在 §3.3.4 统计项登记表登记新 key，避免重复。
   ```

### 3.3 统计项命名与数据格式（强制）

#### 3.3.1 `StatisticType` 扩展规则

1. 新增维度需评审；禁止随意加枚举值。
2. 现有枚举：`pageView`（页面访问）、`click`（点击行为）、`count`（业务计数）、
   `system`（系统异常/基础信息）。

#### 3.3.2 key 命名规则

| 类型 | 格式 | 示例 |
|---|---|---|
| 页面访问 | `page_view_[模块]_[页面]` | `page_view_task_home` |
| 点击行为 | `click_[模块]_[动作]` | `click_task_complete` |
| 业务计数 | `count_[模块]_[指标]` | `count_task_completed` |
| 系统异常 | `system_[类型]` | `system_app_crash` |

#### 3.3.3 数据格式约束

| 字段 | 类型 | 约束 |
|---|---|---|
| `StatisticData.key` | `String` | 遵循 §3.3.2，全项目唯一 |
| `StatisticData.value` | `dynamic` | 计数用 `int`；行为埋点用 `Map`（含实体 id）；系统信息用 `String` |
| `StatisticData.time` | `DateTime` | 取事件发生时刻，禁止事后手工改写 |

#### 3.3.4 统计项登记（新增必须补充）

| key | 模块 | 类型 | 说明 |
|---|---|---|---|
| `page_view_task_home` | Task | pageView | 任务首页访问 |
| `click_task_complete` | Task | click | 完成任务点击 |
| `count_task_completed` | Task | count | 累计完成任务数 |
| `page_view_shop_home` | Shop | pageView | 商城首页访问 |
| `click_shop_exchange` | Shop | click | 兑换点击 |
| `count_points_increase` | Points | count | 积分增加总数 |
| `system_app_crash` | System | system | App 崩溃信息 |

> 维护提示：此表是**人工登记**的，不代表代码全集。改动埋点后应顺手同步本表。

### 3.4 写入时机与存储限制（强制，v2.0 重写）

1. 上报时机：

   | 类型 | 时机 | 注意 |
   |---|---|---|
   | 页面访问 | `initState` | **禁止**在 `build` 中上报（会重复） |
   | 点击行为 | `onPressed` 内异步执行 | 不得阻塞点击响应 |
   | 业务计数 | 数据**已持久化之后** | 否则会出现「记了但没存」 |
   | 系统异常 | `FlutterError.onError` 捕获后 | 需带异常与堆栈 |

2. 存储限制（与代码一致）：
   - 本地缓存上限 **2000 条**，超出丢弃最早数据（`_maxCacheSize = 2000`）；
   - 当前**无任何网络上报**。因此对高频写入要自觉节流 —— 例如小游戏局内得分
     节流为同一局 ≥5 秒一次，**回合结束的最终分数不受节流限制、必须入账**。
3. 失败处理：`report` 自身异常不得向外抛（否则会拖垮调用方业务），
   内部转为 `system_statistic_fail` 记录（若连这也失败则静默，避免递归）。

### 3.5 与 Provider 的对接（强制）

1. 取数必须 `listen: false`，禁止长期持有 Provider 实例。
2. 适配器只读取，**不得**触发 UI 重建。
3. 依赖型数据（如商城统计要先拿积分）应在适配器内先取最新依赖值再计算。

## 四、工程结构规范

### 4.1 目录结构（v2.0 按现状重写）

```
lib/
├── core/                       # 跨模块基础设施（不依赖任何业务模块）
│   ├── config/                 # app_config.dart（常量/DB 名与版本）、cdn_bases.dart
│   ├── errors/                 # app_error / error_handler / result
│   ├── models/                 # base_model、statistic_data
│   ├── router/                 # app_router
│   ├── services/               # 基础服务：database/（按域拆 mixin）、
│   │                           # widget_service、statistic_service、file_downloader
│   ├── storage/                # storage_manager
│   ├── updater/                # 更新引擎：models / services / providers / widgets / pages
│   └── utils/                  # 通用工具：version_utils、date_utils、num_utils 等
├── modules/                    # 业务模块，每个模块自成一个世界
│   └── <业务>/
│       ├── models/ services/ repositories/ providers/ pages/ widgets/
│       ├── adapters/           # 统计适配器
│       └── utils/
├── providers/                  # （历史遗留）跨模块 Provider 的补充位置，新代码优先放模块内
├── ui/                         # 全局 UI 组件
└── main.dart                   # 入口：服务初始化 + MultiProvider + 路由
```

**依赖方向铁律**：`modules/* → core/*` **单向**。`core` 不得 import 任何 `modules`。

> **v2.0 更正**：v1.1 的目录图把 `docs/` 画在 `lib/` 下（实为仓库根目录 `docs/`），
> 且未反映 `core/updater`、`core/storage`、`core/errors`、`core/router`。
> 已按实际目录重画。

### 4.2 命名规则

1. 目录与文件：小写 + 下划线（`task_provider.dart`、`game_cdn_config.dart`）。
2. 类名：大驼峰（`TaskProvider`、`AppUpdateDecider`）。
3. 禁止中文/特殊字符；禁止无意义命名（`utils1.dart`、`page.dart`、`helper.dart`）。
4. 文件名要能推断内容：`app_update_decider.dart` 优于 `decider.dart`。

## 五、编码规范

### 5.1 风格

1. 遵循 Dart 官方风格；提交前跑 `dart format`。
2. 缩进 **2 个空格**（遵循 `dart format` 默认，**不使用 Tab**）。
   > **v2.0 更正**：v1.1 写「4 个空格」，与 `dart format` 的默认（2 空格）
   > 及本项目全部既有代码不符，已改为 2。
3. 单行不超过 **120** 字符。
4. 注释：
   - 公有类/方法用 `///` 说明职责、参数、返回值、**不变量**；
   - 复杂逻辑用行内注释说明「为什么」而不是「做了什么」；
   - 禁止保留注释掉的死代码，禁止拼音注释。

### 5.2 异常处理（强制）

1. 所有异步 I/O（网络、文件、DB）必须捕获异常。
2. 边界层要有**自定义异常类型**（如 `GameException`、`AppUpdateException`、
   `FileDownloadException`），而不是到处抛裸 `Exception`。
3. **跨层委托必须转换异常**：底层抛 `FileDownloadException`，
   游戏模块对外仍抛 `GameException`（`on FileDownloadException catch (e) { throw GameException(e.message); }`），
   保证调用方的 catch 种类不因重构而失效。
4. **禁止空 catch**：至少要记录（`AppLogger` / `debugPrint`）。允许「有意忽略」，
   但必须写明理由注释。
5. 解析外部数据（远程 JSON 等）采用 **fail-soft**：
   - 顶层结构不对 → 抛 `FormatException`（这类错误必须让上层知道）；
   - 单个字段非法 → **只丢弃该字段**，不要整份报废。
6. 安全校验不放行：
   - 下载 URL 只接受 `http` / `https`（拒绝 `file:`、`javascript:`）；
   - 需要校验的产物（APK / 资源包）**先校验哈希，再执行下一步**，
     校验失败绝不允许进入安装/解压/落位。

## 六、单元测试规范

### 6.1 覆盖要求（强制）

1. **Provider**：新增 Provider 必须有测试，覆盖初始化、核心方法、
   `notifyListeners` 触发时机、依赖注入。
2. **Model**：默认值、`copyWith`、序列化/反序列化（含**非法输入**）。
3. **纯函数/决策逻辑**：必须充分覆盖分支。如 `AppUpdateDecider`、`VersionUtils`
   这类无副作用代码是本项目最值得测的部分，**应做到分支级覆盖**。
4. **Widget**：复杂组件的条件渲染与交互回调。
5. 覆盖率目标 ≥ 70%（对 `core/` 应更高）。

### 6.2 测试目录

`test/` 与 `lib/` **不是严格 1:1**，按领域松散组织：

```
test/
├── adapters/  core/  errors/  models/  providers/
├── repositories/  services/  utils/  widgets/
```

`core/` 下的测试保持与 `lib/core/` 同构（如 `test/core/updater/`、`test/core/utils/`），
便于定位。

### 6.3 命名

| 类型 | 格式 | 示例 |
|---|---|---|
| 文件 | `[原文件名]_test.dart` | `app_update_decider_test.dart` |
| 分组 | `group('[类名]', ...)` | `group('AppUpdateDecider', ...)` |
| 用例 | `test('[条件] → [预期]')` | `test('minSupported 更高时 → forced')` |

用例描述用中文、写清条件与预期；断言失败时应能只凭名字定位问题。

### 6.4 Mock

1. 用 `mockito` + `@GenerateMocks([...])`。
2. Provider 测试必须 mock 依赖（Repository / 其他 Provider）。
3. 每个 test 前 `clearInteractions(mock)`。
4. **`verify` 计数陷阱**：对同一调用点连续多次 `verify(m).called(n)` 计数不可靠，
   要断言「调用几次」请用 `thenAnswer` 里的本地计数器（详见 `windows-agent-env-workarounds`）。
5. 需要真实 SQL 的仓储测试用 `sqflite_common_ffi`（dev 依赖，已配置，无需额外准备 dll）。

### 6.5 运行要求

1. 提交前 `flutter test` 全绿。
2. 新增功能必须附带测试。
3. **测试必须能真正失败**：只测「没抛异常」的测试没有价值；
   新写测试时故意破坏一次实现，确认测试会红，再改回来。

## 七、代码量控制规范

### 7.1 硬性上限（强制）

| 类型 | 上限 | 处理 |
|---|---|---|
| 单文件 | **500 行** | 必须拆分 |
| 单类 | **300 行** | 提取组件或 Mixin |
| 单方法 | **50 行** | 拆子方法 |

（对应的拆分操作手册见 skill `dart-large-file-splitting`。）

### 7.2 拆分原则

1. UI：提取为独立 Widget 文件，命名 `[功能]_widget.dart`，放**同目录**，
   数据与回调走构造函数。
2. 逻辑：提取为方法或 Mixin（`[功能]_mixin.dart`），工具类 `[功能]_utils.dart`。
3. Provider：按职责拆分，依赖注入关联。
4. **拆分以「可读性」为目的，不是为数字达标**：拆完要更容易看懂，
   否则说明拆错了维度（常见错误：按代码行数机械对半切）。

### 7.3 禁止行为

1. 为拆分而拆分（50 行文件拆成 10 个）。
2. 拆分后产生循环依赖。
3. 拆分后破坏模块独立性（如把 `tasks` 的内部实现塞进 `core`）。
4. **不改公开 API 的拆分才是好拆分** —— 消费方应零改动（见 `dart-large-file-splitting`）。

## 八、提交与版本规范（v2.0 新增章节）

> v1.1 未涵盖提交约定，导致约定只存在于口头与历史记忆里。本节将其固化。

1. 提交标题：`V5.<minor>.<patch>: 简短描述`（如 `V5.5.11: 新增 App 热更新能力`）。
   描述概括**用户可见的变化**，不写「修改代码」这类无信息量的词。
2. 提交正文：中文，写清 **改了什么 / 为什么 / 怎么验证的**。
3. **中文提交信息必须写成 UTF-8 文件后用 `git commit -F <文件>`**。
   禁止 `git commit -m "中文..."`（命令行参数会被非 UTF-8 控制台编码破坏）。
   提交后用 `git cat-file commit HEAD` 做**字节级回读**确认。
4. 暂存用**限定路径**（`git add lib test`），不要把工具产物（`.flutter_tool_state`、
   IDE 日志、临时 scratch）一起提交。
5. 提交后把 `pubspec.yaml` 的 `version` 与提交号对齐（`5.5.11+0`）。
6. 一次提交只做一件事。功能与它的版本号对齐可以是两次提交。
7. 详细操作步骤与编码坑见 skill `windows-agent-env-workarounds`。

## 九、扩展与迭代规则

1. 本规范随架构演进修订。**修订时保留条款编号**，删除的条款标注原因。
2. 临时需求：代码内标 `// TEMP: <清理时间>-<责任人>`，到期必须清理。
3. 兼容性：`core/` 中对外接口（`StatisticService.report`、`VersionUtils.compare`、
   `CdnBases.resolve` 等）保持向后兼容；内部实现可替换。
